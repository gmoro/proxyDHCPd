## 2024-05-24 - DoS via Unhandled Out-Of-Bounds Exception in Packet Parsing
**Vulnerability:** In `pydhcplib`'s packet parsing logic, `DecodePacket` did not check if the iterator was at the end of the packet data before attempting to read the length byte of a DHCP option (`iterator+1`). A specially crafted packet terminating exactly at an option byte code would throw an `IndexError: list index out of range`, potentially crashing the ProxyDHCP daemon handling the packet.
**Learning:** This existed because the original `pydhcplib` codebase assumed a well-formed network payload and blindly relied on `self.packet_data[iterator+1]`.
**Prevention:** Ensure all binary network data parsing functions bounds-check their read iterators against the maximum buffer length before consuming dynamically-sized tokens.

## 2024-05-24 - Silent Type-Mismatch Bypass in Fixed-Length Network Protocol Field Validation
**Vulnerability:** In `pydhcplib`'s option validation logic (`SetOption`), the comparison `specs == length` evaluated a list against an integer, silently returning `False` without an error. This flaw caused the system to fall back to generic validation rules (minimum length and modulo checking). For fields like "ipv4" where minimum length was 0 and multiple was 1, any payload length was incorrectly accepted. This bypass allowed malformed, truncated network options to be stored and processed by the system.
**Learning:** This bug demonstrates the danger of Python's dynamic typing in protocol parsers. Comparing a list object (e.g. `[4, 0, 1]`) directly with an integer `length` fails silently, resulting in broken conditional logic and bypassing intended security bounds checks without raising warnings.
**Prevention:** Always compare scalar values and use specific list indexing (e.g., `specs[0] == length`) rather than comparing collections against integers. Utilize explicit type checking or strongly typed validation structures when enforcing network protocol specifications in Python.
