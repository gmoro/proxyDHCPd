## 2024-05-24 - DoS via Unhandled Out-Of-Bounds Exception in Packet Parsing
**Vulnerability:** In `pydhcplib`'s packet parsing logic, `DecodePacket` did not check if the iterator was at the end of the packet data before attempting to read the length byte of a DHCP option (`iterator+1`). A specially crafted packet terminating exactly at an option byte code would throw an `IndexError: list index out of range`, potentially crashing the ProxyDHCP daemon handling the packet.
**Learning:** This existed because the original `pydhcplib` codebase assumed a well-formed network payload and blindly relied on `self.packet_data[iterator+1]`.
**Prevention:** Ensure all binary network data parsing functions bounds-check their read iterators against the maximum buffer length before consuming dynamically-sized tokens.

## 2024-05-24 - DoS via Truncated DHCP Options Causing Downstream Type/Index Errors
**Vulnerability:** The packet parsing logic in `proxydhcpd/dhcplib/dhcp_basic_packet.py` failed to validate that an option's stated length byte (`opt_len`) actually fit within the remaining network payload buffer (`end_iterator`).
**Learning:** Because Python's list slicing (`self.packet_data[opt_first+1:opt_len+opt_first+1]`) is overly forgiving and simply returns whatever elements remain without raising an `IndexError`, the parsing loop would silently inject truncated, malformed byte arrays into the packet options dictionary. This shifted the crash out of the network decoding layer and into the downstream business logic (e.g., causing `TypeError`s during IPv4 integer conversions or `IndexError`s during MAC string formatting), resulting in an unhandled exception DoS that would crash the daemon.
**Prevention:** In binary protocols, always explicitly validate that `current_index + expected_length <= max_buffer_length` before extracting fields, as dynamic language slicing semantics may mask buffer over-reads and pollute internal state with truncated data.
